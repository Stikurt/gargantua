## Что повторить без моделей

Из корня экспериментальной ветки:

```powershell
npm ci
node --test tests/audio.test.mjs tests/audio-engine.test.mjs tests/audio-requests.test.mjs tests/book-audio.test.mjs tests/native-audio.test.mjs tests/derived-audio-plan.test.mjs tests/desktop-audio-proof.test.mjs
python -m unittest discover -s inference -p 'test_*.py' -v
python inference/freeze_profiles.py --check
docker compose config --quiet
docker compose build
```

`npm run test:legacy` запускает более широкий исторический набор; часть интеграционных сценариев требует отдельной тестовой БД/библиотеки. Не выдавайте пропущенные тесты за пройденные. Не подставляйте рабочий `DATABASE_URL` в интеграционные фикстуры. Закреплённые runtime, веса и свежий монитор нужны только для реального синтеза, не для большинства чистых модульных тестов.

После отдельной Windows-сборки можно повторить настоящий клиентский плеер:

```powershell
./scripts/test-audio-client.ps1 -DesktopExe './releases/Gargantua-Audio-Experimental/Cotology.exe'
```

Используется собственный loopback-сервер, отдельный профиль self-check и технический WAV; модели не загружаются. Для уже созданного WAV добавьте `-SamplePath '<полный путь к своему WAV>'`. Отчёты появляются в `.local/audio-client-check`; перед публикацией удалите приватные пути, адреса и пользовательские данные.

## Реальная приёмка после установки

1. Поднимите отдельный экспериментальный сервер по `SETUP_AUDIO.md`; проверьте здоровье, свежий ClamAV и работающие монитор/daemon.
2. Через клиент импортируйте собственный русский текст из нескольких коротких глав. Запросите озвучку и проверьте реальное появление завершённых сегментов; повтор не должен создавать дублирующую работу.
3. Прервите обработку штатно между подтверждёнными сегментами. Сохраните хеши готовых файлов; после нового запуска проверьте их неизменность и завершение оставшихся.
4. Через клиент скачайте весь результат. Проверьте порядок, паузу, перемотку, скорость, переходы и независимость позиции текста от аудио.
5. Остановите сервер, закройте клиент, откройте новым процессом и воспроизведите сохранённое. Убедитесь, что отсутствие сети не выдаётся за успешную загрузку ещё не сохранённых фрагментов.
6. На Android отдельно проверьте фон, выключение экрана, системное управление медиасессией, возвращение в приложение и завершённую книгу. Новые устройства, Doze, батарея, Bluetooth/гарнитура и звонки требуют собственной проверки.

Проверка качества голоса на слух, литературного перевода и семантической полноты речи остаётся отдельной задачей. Исторические статусы `NOT_LISTENED`, `MACHINE_DRAFT`, `NOT_FULLY_SCANNED` сохраняются. Испытание микрокниги или одной 15-минутной главы не означает, что полная аудиокнига/многодневная очередь испытана.

## Что добавлено для публикации

Веточные `compose.yaml`, `index.html` и помощник `prepare-audio-experimental.py` восстанавливают отдельный путь запуска старого сервера/клиента и загрузку закреплённых зависимостей из свежего клона. Они не требуют личного адреса автора. Факт сборки и проверки этих файлов при подготовке публикации должен быть указан отдельно в итоговом отчёте; приведённые выше исторические числа не засчитываются новой публикации автоматически.

Проверка экспорта 24 октября 2026: чистая Docker/Vite-сборка успешна, Compose config корректен; семь файлов аудиотестов — **129 пройдено, 0 ошибок, 1 Windows-only пропущен в Linux**; Python — **45/45**; проверка согласованности профилей `freeze_profiles.py --check` успешна. Реальные модели и синтез заново не запускались, новая веточная приёмка на телефоне не заявляется. Среди сохранённых npm-зависимостей обновлены body-parser 2.3.0 → 2.4.0 и multer 2.4.0 → 2.5.0; прикладной аудиокод сохранён. У Python-тестов временные файлы перенесены в системный temp: первоначальный прогон в глубоком клоне дал четыре ошибки длины Windows-пути, повтор с исправленным тестовым каталогом прошёл целиком. Неудачный первый Docker-прогон не содержал вспомогательный scripts-модуль; повтор с полной тестовой source closure успешен.
